<tasks>
  <task id="1" type="design-check">
    <name>Confirm existing UI graph/component architecture</name>
    <action>
Map current UI components, control-server endpoints, graph state types, and runtime event streams. Identify the smallest integration path for typed node composer data without replacing unrelated UI infrastructure.
    </action>
    <acceptance_criteria>
Plan implementation has concrete target files and does not depend on guessing current UI structure.
    </acceptance_criteria>
  </task>

  <task id="2" type="implementation">
    <name>Add typed composer state contract to UI/control API</name>
    <action>
Expose node type, runtime/model, prompt/code config, typed ports, artifact schema summary, complexity, plan budget, and artifact refs through the UI graph state. Preserve compatibility for existing graph nodes.
    </action>
    <acceptance_criteria>
UI can render a typed node composer from control-server graph state without embedding large artifact payloads.
    </acceptance_criteria>
  </task>

  <task id="3" type="implementation">
    <name>Build ComfyUI-style typed node composer</name>
    <action>
Render dense graph nodes with always-visible type/runtime/prompt-or-code controls, typed ports, context policy, budget display, complexity label, and plan/run/breakdown/delete controls.
    </action>
    <acceptance_criteria>
User can enter a prompt into an editable root node and see the node as a typed dataflow module with visible controls.
    </acceptance_criteria>
  </task>

  <task id="4" type="implementation">
    <name>Implement node-local Plan preview</name>
    <action>
Wire the node `Plan` action to create or request an editable pending child graph. Children must include type, summary, typed ports, complexity, and budget impact. Do not execute planned children until explicit approval.
    </action>
    <acceptance_criteria>
Clicking Plan on a node produces pending child nodes and no execution starts silently.
    </acceptance_criteria>
  </task>

  <task id="5" type="implementation">
    <name>Add recursive budget and complexity UX</name>
    <action>
Display remaining plan depth/node budget and complexity per node. Provide `Break down` for high-complexity nodes. When budget is exhausted, pause expansion and require explicit `Extend budget`.
    </action>
    <acceptance_criteria>
Recursive planning cannot run away; the UI shows what limit was hit and how to approve extension.
    </acceptance_criteria>
  </task>

  <task id="6" type="implementation">
    <name>Expose artifact refs and book-scale context policy</name>
    <action>
Render artifact refs/metadata in nodes and expose context policy summaries for reads, writes, token/window limits, batching, and memory scopes. Use the audiobook workflow as an internal test fixture or documented example.
    </action>
    <acceptance_criteria>
The UI can explain, through node state, how a full-book workflow processes chunks and audio refs without loading the full book/audio into model context.
    </acceptance_criteria>
  </task>
</tasks>

<verification>
- Unit/component tests for typed node composer rendering.
- Control-server/API tests for Plan creating pending child graph state without execution.
- Budget exhaustion test: expansion pauses and requires explicit extension approval.
- Artifact-ref test: large artifact metadata renders without payloads in graph state.
- Manual UI walkthrough: launch UI, enter root prompt, Plan, inspect pending children, Break down a high-complexity child, approve run.
</verification>

<success_criteria>
- Root composer is the first-run authoring surface.
- Nodes behave as typed dataflow modules with ports and artifact refs.
- Plan mode creates editable pending child graphs.
- Recursive decomposition is visible and bounded.
- Code-only and TTS/audio workflows are naturally represented in the composer.
</success_criteria>
